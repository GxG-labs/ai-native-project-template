# Компиляция знаний

Используйте этот метод, когда знание по теме должно улучшаться по мере
поступления новых материалов.

## Три слоя

```text
context/sources/<topic>/   → сырой материал и первоисточники
ai/methods/<topic>.md      → playbook: сжатое проверяемое руководство
ai/skills/<topic>/SKILL.md → процедура, которую можно выполнять повторно
```

Каждый следующий слой ссылается на предыдущий. Сырые материалы не удаляют
после компиляции. Playbook не является skill: он объясняет, что делать и
почему; skill описывает воспроизводимую процедуру.

## Каноническая конфигурация и снимок запуска

Если скомпилированное знание используется автоматически, текущая папка
`tenant/config/` является единым источником правды для новых запусков. Она
содержит готовый tenant- или project-specific runtime-пакет: голос, point of
view, ограничения, выбранные библиотеки и другие настройки.

Перед началом автоматического запуска выбранный пакет фиксируется в
неизменяемом snapshot:

```text
tenant/config
  -> run snapshot
      + manifest
      + package version
      + source references
      + source/package hashes
      + compilation timestamp
```

Копирование в run — намеренная фиксация исторического контекста, а не второй
источник правды. Изменение канонического пакета влияет только на новые runs;
старый run должен оставаться воспроизводимым и объяснимым.

Минимальные правила:

- канонический пакет в `config/` не редактируется вручную, если файл является
  generated output;
- его манифест имеет версию и дату компиляции;
- snapshot фиксирует версии или хэши использованных источников;
- после старта run snapshot не меняется;
- профиль или конфигурация выбирают пакет, но не дублируют его содержимое;
- скомпилированное наблюдение не может молча перезаписать ручное правило.

## Raw, curated и языковые датасеты

Для tenant-specific знаний используйте простую последовательность:

```text
raw -> curated -> config -> run snapshot
```

- `raw/` — сырые брендбуки, документы, заметки и исходные примеры;
- `curated/` — вручную отобранные и подготовленные канонические материалы;
- `config/` — готовый канонический runtime-пакет, включая compiled observations;
- `run snapshot` — неизменяемая копия, использованная конкретным запуском.

Если tenant работает на нескольких языках, полнотекстовые style-примеры
хранятся раздельно:

```text
tenants/<tenant>/
  raw/
  curated/
    voice.md
    point-of-view.md
    examples/
      ru/
        good/
        bad/
      en/
        good/
        bad/
  config/
    voice.md
    point-of-view.md
    style.ru.yaml
    style.en.yaml
    linkedin.yaml
    manifest.yaml
```

Общие `voice.md` и `point-of-view.md` содержат языконезависимое ядро. Отдельные
языковые правила добавляются только при реальной необходимости, а не для
симметрии каталогов. Компилятор строит `style.ru.yaml` только из русских
примеров, а `style.en.yaml` — только из английских. Evidence одного языка
нельзя молча применять к другому.

Файл канальной конфигурации, например `linkedin.yaml`, выбирает язык, voice,
point of view, библиотеки и соответствующий compiled style внутри канонического
пакета `config/`.

## Владение и формат артефактов

Формат файла не определяет его владельца. Сначала определяется жизненный цикл
и ответственность, затем выбирается формат, удобный для этой ответственности.

### Skill

Skill содержит повторяемую процедуру, а не данные конкретного tenant:

```text
ai/skills/<skill-id>/
  SKILL.md             # входы, шаги, выходы, проверки и ограничения
  references/          # нужные пояснения и ссылки
  templates/           # шаблоны результата
```

В skill можно хранить общие правила канала или процесса, если они нужны всем
потребителям этого skill. Tenant-specific голос, POV, ограничения и примеры в
skill не копируются.

### Libraries и skill configuration

Библиотеки содержат переиспользуемые наборы вариантов, которые процедура
перебирает или выбирает: форматы, категории, персонажи, методы, признаки,
шаблоны и допустимые значения.

Конфигурация skill задаёт поведение процедуры: defaults, включённые библиотеки,
пороговые значения, порядок шагов и доступные режимы. Она не должна содержать
ручную бренд-специфику tenant.

Выбирайте формат по структуре данных:

- **CSV** — плоский табличный реестр с повторяющимися однотипными строками:
  категории, форматы, методы, признаки, примеры с фиксированными колонками;
- **YAML или JSON** — иерархическая конфигурация, manifest, profile, правила
  выбора, вложенные параметры и машинные контракты;
- **Markdown** — объяснения, правила, ограничения, rationale и материалы,
  которые должны читаться человеком;
- **папки примеров** — good/bad или другие артефакты, где важен полный текст,
  а не только табличные поля.

Не превращайте CSV в универсальный формат: если строки имеют разные поля,
вложенность или сложные связи, используйте YAML/JSON или отдельные Markdown-
артефакты.

### Tenant configuration

Tenant-конфигурация выбирает и ограничивает общий skill:

```text
tenant config
  -> enabled libraries
  -> allowed/excluded categories
  -> locale and audience
  -> voice and point of view references
  -> tenant-specific constraints
```

Она может быть YAML/JSON для настроек и CSV для tenant-specific реестров, но не
должна встраивать в себя логику skill. Канонические tenant-знания (например,
`voice.md`, `point-of-view.md`, good/bad-примеры) хранятся отдельно от
конфигурации и компилируются в runtime package.

Правило границы:

```text
skill отвечает за «как делать»
library отвечает за «какие варианты доступны»
tenant config отвечает за «что разрешено этому tenant»
tenant knowledge отвечает за «кто этот tenant и как он мыслит»
compiled package отвечает за «что именно использовал новый run»
run snapshot отвечает за «что использовал исторический run»
```

## Когда перекомпилировать

Пересоберите playbook после появления существенного источника, опровержения
старого правила или обнаружения повторяющейся ошибки. Затем обновите skill,
если изменился его процесс, вход, выход или проверка.

## Минимальная структура playbook

- Назначение и границы темы.
- Правила, исключения и ссылки на исходные материалы.
- Дата последней компиляции.
- Что должно быть подтверждено до применения.

Не создавайте skill, пока playbook не описывает устойчивую повторяемую
процедуру.
