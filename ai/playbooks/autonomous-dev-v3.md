# Автономная разработка, v3

## Назначение

Как организовать автономную разработку с Claude Code так, чтобы агент делал
максимум работы сам, сервисов было минимум, а человек контролировал каждое
решение, требующее суждения.

v3 объединяет два предыдущих документа:

- `ai-native-sdlc.md` (v2) — цепочка версионируемых артефактов;
- `autonomous-dev-plan.md` (v1) — набор плагинов, проверок и защит.

Из v2 берётся «что и кто утверждает», из v1 — «чем проверяем». Новое в v3:
контроль держится на детерминированных гейтах, а не на тексте инструкций, и
большая часть того, что в v1 решалось плагинами, теперь встроена в Claude Code.

Версии и флаги сверены с документацией Claude Code 2026-11-21 (v2.1.32x).
Перед настройкой сверяйте их снова: они меняются еженедельно.

---

## 1. Принципы

1. **Узкое место — проверка, а не генерация.** Код пишется быстро. Медленные
   шаги — утверждение, ревью, релиз. Процесс строится вокруг них.
2. **Каждый этап оставляет файл в git.** Следующий этап читает файл, а не
   историю чата. Коммиты — журнал аудита.
3. **Инструкция советует, гейт обеспечивает.** CLAUDE.md и skills — контекст.
   Правило без исключений живёт в hook, permission deny или CI.
4. **Агент не принимает собственную работу.** Финальную проверку делает чистый
   контекст: subagent-верификатор, `/code-review`, CI, человек.
5. **Одна команда — один ответ.** Каждая проверка — одна команда с ненулевым
   кодом выхода при ошибке. Без неё автономный цикл не знает, когда остановиться.
6. **Минимум сервисов.** Claude Code + git + GitHub + CI. Всё остальное
   добавляется только под конкретную боль.

## 2. Цепочка артефактов и точки контроля

| Этап | Артефакт | Кто пишет | Кто утверждает | Что запускает следующий этап |
|---|---|---|---|---|
| Намерение | `intent/<change>/intent.md` | человек с агентом | владелец продукта (вы) | принятый intent |
| Требования | `docs/spec/<scope>/spec.md` | агент | вы | принятый spec |
| План | `docs/plan/<change>/plan.md` | агент в plan mode | вы | одобренный план |
| Реализация | ветка, код, тесты | агент в auto mode | гейты (hooks, тесты) | зелёные проверки |
| Ревью | PR + отчёт проверки | агент + верификатор | вы | merge |
| Эксплуатация | инцидент / метрика | наблюдение | вы | новый `intent.md` |

Правила:

- `spec.md` нужен, только когда меняются требования или архитектура.
- `plan.md` нужен для нетривиального или рискованного изменения. Для мелкой
  правки хватает плана в plan mode без файла.
- Описание текущей реализации не ведётся: её источник правды — код, тесты,
  конфигурация и git.
- Если реализация расходится с принятым решением, сначала обновляется spec или
  plan, потом код.

## 3. Пять слоёв контроля

Каждое правило живёт ровно в одном слое. Если правило не держится, его
переносят на слой ниже, а не усиливают формулировку.

| Слой | Что делает | Чем реализован | Сила |
|---|---|---|---|
| 1. Контекст | объясняет цель, команды, соглашения | `RULES.md` через `CLAUDE.md`, path-scoped rules | совет |
| 2. Процедуры | повторяемые способы работы | skills (`SKILL.md`) | совет |
| 3. Гейты | запрещают и требуют | permissions `deny`, hooks `PreToolUse`/`Stop`, pre-commit | жёстко, локально |
| 4. Независимая проверка | ищет ошибки автора | subagent-верификатор, `/code-review`, CI | жёстко, вне автора |
| 5. Человек | решения, требующие суждения | утверждение intent/spec/plan, merge | финально |

Что важно знать о слое 1:

- Claude Code сам читает `CLAUDE.md` и импорты `@path` (до 4 уровней).
  Фраза «прочитайте RULES.md» в CLAUDE.md — просьба; строка `@RULES.md` —
  гарантированная загрузка.
- `AGENTS.md` Claude Code читает только при отсутствии `CLAUDE.md`. Для
  мульти-агентного проекта оставляйте оба адаптера, каждый с указателем на
  `RULES.md`.
- Ориентир — меньше 200 строк на файл инструкций. Длинный файл снижает
  соблюдение всех правил сразу. Правила для части кода выносите в
  `.claude/rules/*.md` с `paths:`, они грузятся только при работе с этими
  файлами.
- Добавляйте правило после повторной ошибки агента, а не заранее.
- `/context all` показывает, что реально загрузилось.

## 4. Минимальный стек

### Обязательно

| Что | Зачем |
|---|---|
| Claude Code (CLI или Desktop) | исполнитель |
| git + GitHub (Free) | артефакты, ветки, PR |
| Одна команда проверки (`npm test` / `make check`) | критерий «готово» |
| `.claude/settings.json` в репозитории | permissions и hooks — гейты слоя 3 |
| GitHub Actions на каждый PR | проверка вне машины агента |

### Встроено в Claude Code — плагины не нужны

| Задача | Встроенное средство | Чем заменяет v1 |
|---|---|---|
| Спецификация до кода | plan mode (`Shift+Tab`, `/plan`) | Superpowers |
| Работа до выполнения условия | `/goal <условие>` | ralph-loop |
| Работа без постоянных подтверждений | auto mode (классификатор действий) | — |
| Независимое ревью diff | `/code-review` (свежий subagent) | pr-review |
| Сборка и запуск приложения | `/verify` | — |
| Параллельные задачи | `claude --worktree <name>`, `/batch` | — |
| Бэкграунд и облако | `claude --cloud`, `/tasks`, Auto-fix для PR | — |

### По необходимости (официальный маркетплейс `claude-plugins-official`)

- `commit-commands` — коммит, push и PR одной командой.
- `typescript-lsp` / `pyright-lsp` — точная навигация по коду вместо grep.
- `security-guidance` — если код касается авторизации, платежей, ПД.
- `hookify` — если хотите писать hooks в markdown, а не в JSON.
- `playwright` — браузерные тесты, когда появится UI.

### Не ставить без конкретной причины

- Superpowers: его нет в официальном маркетплейсе, а plan mode закрывает ту же
  задачу.
- ralph-loop: `/goal` и `Stop`-hook делают то же со встроенным лимитом.
- Внешние трекеры, оркестраторы, MCP-серверы «на будущее». Каждый сервис — это
  токены в контексте, ключ доступа и точка отказа.

## 5. Конфигурация гейтов

### 5.1. Permissions (`.claude/settings.json`, в git)

```json
{
  "permissions": {
    "defaultMode": "plan",
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(git push --force*)",
      "Bash(git push origin main*)",
      "Edit(./RULES.md)",
      "Edit(./PROJECT.md)",
      "Edit(./PROJECT_STRUCTURE.md)",
      "Edit(./SECURITY.md)",
      "Edit(./PRIVACY.md)",
      "Edit(./.github/workflows/**)"
    ]
  }
}
```

- `deny` действует во всех режимах, включая auto.
- `defaultMode: "plan"` — каждая сессия начинается с плана.
- `auto` нельзя задать в настройках проекта: только в `~/.claude/settings.json`
  или при одобрении плана («Yes, and use auto mode»). Это правильно: решение о
  свободе агента — ваше, на вашей машине.
- Защищённые файлы снимаются с `deny` только на время явной просьбы человека.

### 5.2. Hooks

Скрипты хуков лежат в `scripts/hooks/`, в `.claude/settings.json` — только
ссылки на них. Так скрытая папка остаётся routing-конфигом.

| Hook | Что делает | Почему не CLAUDE.md |
|---|---|---|
| `PreToolUse` на `Bash` | блокирует `git push` и `git commit`, если текущая ветка `main` | на GitHub Free у приватного репо нет защиты веток |
| `Stop` | если есть незакоммиченные изменения в `src/` или `tests/`, запускает проверку; при ошибке возвращает агента к работе | «запусти тесты перед завершением» агент забывает |
| `PostToolUse` на `Edit\|Write` | форматирование (когда появится форматтер) | экономит итерации ревью |

Правила для `Stop`-hook:

- выходить сразу, если во входных данных `stop_hook_active: true`;
- код выхода 2 возвращает агента к работе, stderr становится причиной;
- встроенный предел — 8 возвратов подряд, затем ход завершается.

### 5.3. Верификатор

`.claude/agents/verifier.md` — subagent с `tools: Read, Grep, Glob, Bash`.
Его задача: прогнать команду проверки, сверить diff с intent/spec/plan и вернуть
отчёт. Он не исправляет код. Агент-автор запускает его перед открытием PR и
вставляет отчёт в описание PR.

Инструкции верификатора — это процедура, поэтому её тело живёт в
`ai/skills/verify-change/SKILL.md`, а файл агента ссылается на skill.

### 5.4. CI (`.github/workflows/check.yml`)

- На каждый PR: та же команда проверки, что локально.
- Ревью агентом в CI (`anthropics/claude-code-action@v1`) подключайте, когда
  PR станет больше, чем вы успеваете читать. Каждый запуск тратит токены.
- Изменение `RULES.md`, skills или hooks — повод прогнать evals, когда они
  появятся (`evals/`).

## 6. Режимы запуска

| Ситуация | Как запускать | Лимит |
|---|---|---|
| Обычная задача | plan mode → одобрить план → auto mode | вы читаете план |
| Длинная задача с ясным критерием | `/goal "npm test проходит и критерии из plan.md выполнены"` | `Stop`-cap, бюджет сессии |
| Несколько независимых задач | по одной сессии на задачу в своём worktree | одна ветка — одна задача |
| Задача, пока вас нет | облачная сессия или scheduled task | только PR, без merge |
| Скрипт и CI | `claude -p "..." --permission-mode dontAsk --allowedTools ... --max-turns N --max-budget-usd X` | явный allowlist |

- `claude -p` без указанного режима стартует в Manual: всё, что требует
  подтверждения, отклоняется. Это безопасное поведение по умолчанию.
- `--dangerously-skip-permissions` — только в изолированном контейнере.
- Worktrees от `claude -p --worktree` не удаляются сами: чистите после merge.

## 7. Цикл одной задачи

1. **Intent.** Вы описываете проблему и приёмочные критерии простыми словами.
   Агент оформляет `intent.md`, вы правите и принимаете.
2. **Spec**, если меняются требования. Агент пишет, вы принимаете.
3. **Plan.** Агент в plan mode изучает код и предлагает план: файлы, порядок,
   риски, команда проверки. Для крупной задачи план сохраняется в `plan.md`.
4. **Ветка.** Агент создаёт `feat/<change>` (или worktree). Hook не даст
   коммитить в `main`.
5. **Тесты первыми.** Для бага — падающий тест до исправления. Тест не
   редактируется, чтобы он прошёл.
6. **Реализация в auto mode.** Агент работает до зелёной проверки; `Stop`-hook
   не даёт закончить с красной.
7. **Независимая проверка.** Верификатор или `/code-review` в свежем контексте.
   Агент исправляет найденное.
8. **PR.** Описание: что изменилось, вывод проверки, отчёт верификатора, что
   посмотреть руками. CI повторяет проверку.
9. **Merge — только вы.**
10. **Обратная связь.** Ошибка, которую агент повторил, становится правилом
    (слой 1), процедурой (слой 2) или гейтом (слой 3) — в зависимости от того,
    насколько она недопустима. Инцидент становится новым `intent.md` и, когда
    есть `evals/`, новым eval.

## 8. Лимиты и бюджет

- На каждый автономный запуск: критерий готовности, лимит ходов или бюджет,
  граница (ветка или worktree), подпись человека перед merge.
- Auto mode сам откатывается к подтверждениям после 3 блокировок подряд или 20
  всего. Если это случилось — задача плохо описана, а не агент упрямый.
- Минуты GitHub Actions (2 000/мес на Free для приватного репо): быстрые тесты
  на каждый PR, долгие — перед merge.
- Субагенты и параллельные сессии стоят токенов. Запускайте их ради чистого
  контекста или реальной параллельности, а не по привычке.

## 9. Как понять, что процесс работает

| Показатель | Что значит рост |
|---|---|
| CI зелёный с первого раза | агент сам доводит до проверки |
| Доля PR, принятых без доработки | план и критерии были ясны |
| Число правок после merge (rework) | проверка пропускает ошибки |
| Время от intent до merge | где сидит узкое место |

Смотрите раз в две недели. Если метрика плохая, ищите слой, который не
справился, и переносите правило ниже.

---

## 10. Ограничения

- Зелёные тесты подтверждают только то, что описано. Сценарии проверки
  задаются в intent или plan до реализации.
- Безопасность, платежи и персональные данные смотрит человек, даже при
  зелёном CI.
- На GitHub Free защита `main` держится на hook и permissions на вашей машине.
  Облачная сессия их тоже читает из репозитория, но человек с правами записи
  может обойти их. Это осознанный риск тарифа.
- Prompt- и agent-hooks решают моделью — это не жёсткий гейт.

## 11. Трансформация текущего проекта

Найденные расхождения:

1. **Битая маршрутизация.** `ai/methods/` переименована в `ai/playbooks/`, но
   `RULES.md`, `PROJECT_STRUCTURE.md`, `ai/playbooks/organization.md`,
   `ai/playbooks/ai-native-sdlc.md` и `ai/workflows/software-change.md` всё ещё
   ссылаются на `ai/methods/`. Агент, следующий RULES.md, не найдёт файлы.
2. **Адаптеры не загружают правила.** `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`
   просят прочитать `RULES.md`, но не импортируют его.
3. **Нет слоя 3.** Нет `.claude/settings.json`: защищённые файлы, `main` и
   `.env` охраняются только текстом.
4. **Нет слоя 4.** Нет CI и верификатора; проверка — только `npm test` на
   машине автора.
5. **Нет команды полной проверки.** `npm test` собирает и тестирует, линтера
   нет.
6. **Язык.** `RULES.md` требует писать файлы проекта на английском, а
   playbooks и workflows — на русском. Нужно решение человека.

Порядок трансформации — каждый шаг отдельным PR:

| # | Шаг | Слой | Нужно ваше решение |
|---|---|---|---|
| 1 | Починить ссылки `ai/methods` → `ai/playbooks` (RULES.md и PROJECT_STRUCTURE.md — с вашего разрешения) | 1 | да: защищённые файлы |
| 2 | `CLAUDE.md` → `@RULES.md`; `AGENTS.md`, `GEMINI.md` — указатели | 1 | нет |
| 3 | `.claude/settings.json`: `defaultMode: plan` + `deny` из 5.1 | 3 | да: список deny |
| 4 | `scripts/hooks/guard-main.sh` и `scripts/hooks/stop-check.sh` + подключение | 3 | нет |
| 5 | `npm run check` = build + test (+ lint, когда появится) | 3 | нет |
| 6 | `ai/skills/verify-change/SKILL.md` + `.claude/agents/verifier.md` | 4 | нет |
| 7 | `.github/workflows/check.yml` с `npm run check` | 4 | да: правка CI |
| 8 | Обновить `ai/workflows/software-change.md` под цикл из раздела 7; v1 и v2 оставить как источники | 1–2 | нет |
| 9 | Через 2 недели: сверить метрики раздела 9, решить про `claude-code-action` и evals | 4 | да |

Шаги 2–6 независимы и могут идти параллельно в отдельных worktrees.
